# Git開発作業の標準手順書

このドキュメントは、Gitを用いたチーム開発において新しいクラスの作成や既存機能の追加・修正を行う際の標準的な作業手順をまとめたものです。ソースコード編集に特化せず、誰が読んでも実行できるよう、汎用的かつ初心者にやさしい構成としています。

## 1. 作業開始前の準備

### 1.1 SourceTreeの起動とブランチ確認

1. SourceTreeを開きます。
2. 左ペインで現在のカレントブランチが `develop` であることを確認します。

### 1.2 フェッチとPull

1. 上部メニューの「フェッチ」ボタンを押して、リモートに更新があるか確認します。
2. `develop` ブランチに変更がある場合は「Pull」を実行します。
3. 確認ダイアログで `origin → develop` になっていることを確認し、Pullを確定します。

#### 用語解説

- フェッチ：リモートリポジトリから変更履歴を取得しますが、ローカルにはまだ適用されません。
- Pull：リモートの更新をローカルのブランチに反映させる操作です。

## 2. 作業ブランチの作成

### 2.1 既存ブランチの確認と活用

既存の作業ブランチが再利用できるかを確認し、適切であれば新規作成せずに活用します。

1. 左ペイン下部の「リモート」ブランチ一覧から、類似の目的を持つブランチが存在していないか確認します。
2. 既存ブランチが十分に汎用的で、粒度が適切であり、未マージである場合はそれをチェックアウトして作業を行います。
3. 作業に影響が出ないように、必要に応じて `develop` の最新状態を取り込んでから作業を始めます。

#### 用語解説

- 粒度：作業範囲の細かさを表す言葉で、1ブランチにつき1機能が原則です。
- チェックアウト：対象のブランチに作業ベースを切り替える操作です。

### 2.2 新しいブランチを切る

1. カレントブランチが `develop` であることを再度確認します。

2. 「ブランチ作成」ボタンを押します。

3. 以下のような命名規則に従って新しいブランチを作成します：



feature/backend-<カテゴリ>-<目的>

例：

feature/backend-shared-interval

作成後、自動的にそのブランチにチェックアウトされます。

#### 用語解説

- ブランチを切る：新しく作業用のブランチを作成することです。
- チェックアウト：作業対象のブランチを切り替える操作です。

## 3. ソースコードの編集

### 3.1 エディタの選択

推奨エディタは Visual Studio Code（VSCode）です。Python開発に適した環境を整えることができます。

※初学者への配慮として、PyCharm などの IDE は導入せず、キャッシュの管理を簡潔にする目的で `.gitignore` の使用を前提とします。

### 3.2 クラスの作成

1. 新しいクラスや関数を `shared/utils/` などの適切なディレクトリに配置します。
2. 最低限のバリデーションや、再利用性を意識した実装を心がけます。
3. 必要であれば定数やEnumなどの構成要素を追加して使いやすくします。

#### 用語解説

- `.gitignore`：Gitの追跡対象から特定のファイルやフォルダを除外するための設定ファイルです。
- Enum（列挙型）：決められた定数の集合を扱うための構文です。

## 4. ステージングとコミット

### 4.1 ステージング

1. SourceTree の「コミット」画面を開きます。
2. 変更したファイルが下段に表示されます。
3. 右下の差分表示で内容を確認し、編集したファイルのみを `+` ボタンでステージします。

### 4.2 コミット

1. ステージが完了したら、1目的＝1コミットのルールでメッセージを記述します。
2. メッセージは以下の形式に従って書きます：

:&#x20;

例：

feat: 時間ユーティリティクラスを追加

Intervalクラスをshared/utilsに実装しました。
定数を複数追加し、再利用性を考慮しました。

#### 用語解説

- ステージ：Gitでコミット対象としてマークする操作です。
- コミット：変更内容をリポジトリに記録する操作です。

## 5. Pushとマージ

### 5.1 Pushの実行

作業内容をリモートに反映させるには、以下の操作を行います。

1. 「Push」ボタンを押します。
2. 作業ブランチが正しく選ばれていることを確認します。
3. Pushを実行し、完了したことを確認します。

### 5.2 developブランチへのマージ

1. `develop` ブランチにチェックアウトします。
2. マージしたい作業ブランチを選択し、上部の「マージ」ボタンを押します。
3. 確認ダイアログでマージ対象を再確認し、確定します。
4. マージが完了したら、必ず `develop` ブランチの変更をリモートにPushします。

#### 補足

- マージ前に `develop` が最新であるかどうか確認し、必要に応じてフェッチおよびPullを行ってください。
- コンフリクトが発生した場合は一時ブランチに退避し、Discordの「コンフリクトマネジメント」チャネルで相談します。

この手順書は、新機能の実装だけでなく、既存機能の修正や改善にも適用可能です。
常に最新の状態から作業を始め、粒度の適切なブランチ設計・履歴管理を心がけましょう。

## 6. 命名とメッセージのベストプラクティス

### 6.1 ブランチ粒度とスコープの定義指針

作業ブランチの粒度は、1つの目的・変更に対して1ブランチを原則とします。

### OKな例：

- Intervalクラスを新規追加する
- 通知設定APIを実装する
- WPFの休憩モードUIを調整する

### NGな例：

- AFK監視全体を作り直す
- 画面・DB・APIをすべてまとめて実装する
- shared以下を全部整理する

#### 判断のヒント：

- GitHubのPull Requestで「レビュー可能なサイズ」か？
- チームメンバーが「何を変更したのかすぐ分かる」か？
- 将来、変更履歴から機能単位で追えるか？

#### 補足：

やむを得ず粒度が大きくなる場合は、作業ブランチの中でローカルコミットを丁寧に分け、段階的なレビューが可能な状態を維持しましょう。

### 6.2 ブランチ名の命名規則

ブランチ名にはアンダースコア（`_`）ではなく、ハイフン（`-`）を使用してください。
これは視認性・ツール連携・コマンド操作の一貫性の観点から、プロジェクト全体で統一されています。

以下の形式に従ってブランチを命名してください：

- type: feature, fix, chore, hotfix など
- layer: backend, frontend, shared など
- domain: 対象となる機能・コンポーネント名
- summary: 処理内容を簡潔に記述

例：

feature/backend-shared-interval
fix/frontend-ui-login

### 6.3 コミットメッセージの記述指針

コミットメッセージは以下の形式を基本とします：

&#x20;

#### type の一覧例：

- feat: 新機能の追加
- fix: バグ修正
- refactor: 挙動変更なしのコード整理
- docs: ドキュメントのみの変更
- chore: ビルドやCI設定などの雑務

#### ルール：

- subject は命令形（例：Add, Fix）で50文字以内
- 必要に応じて body に詳細な背景・影響範囲を書く
- 互換性のない変更は footer に `BREAKING CHANGE:` を明記

#### 例：

refactor: タイマー管理クラスの構造を整理

コールバック処理の重複を削除し、テスト性を向上させました。
依存性注入に備えた構造に変更しています。

BREAKING CHANGE: 引数の仕様が変更されています。
